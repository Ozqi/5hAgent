# Stage 2 导读

这一阶段对应 `learn/stage-2-tools-task`。

如果说 Stage 1 是“先把 Agent 跑起来”，那 Stage 2 就是在回答另一个更现实的问题：当 Agent 开始真的帮你做事时，输出体验、工具能力、上下文长度这些问题该怎么处理。

这一阶段还是沿着前一阶段的主线往前走，但重点已经从“最小可运行”变成“开始像一个能持续工作的 Coding Agent”。

## 这一阶段新增了什么

- 流式输出，也就是模型一边生成，终端一边显示
- 更多基础工具，比如 `glob`、`edit`、`write_file`、`grep`、`list_dir`
- 工具执行策略优化，开始区分只读工具和写工具
- 自动上下文压缩，避免对话越来越长后难以继续
- 更完整的日志和任务基础设施

你可以先把几个新名词这样理解：

- `Streaming`：不是等模型全部想完再一次性输出，而是边生成边显示
- `glob`：按文件名模式匹配文件，比如找所有 `*.go`
- `edit`：对已有文件做局部替换，而不是整个重写
- `上下文压缩`：当对话太长时，把旧内容收缩成更短的摘要，保留关键信息
- `只读工具并行`：多个不会修改状态的工具可以一起跑，加快反馈速度

## 推荐阅读顺序

建议按下面顺序读：

1. [doc/phase2_summary.md](./phase2_summary.md)
   先看这一阶段到底解决了哪些问题，建立整体印象。
2. [doc/agent.md](./agent.md)
   再回到 Agent 主循环，看流式输出和工具执行策略是怎么接进来的。
3. [doc/context.md](./context.md)
   理解为什么对话一长就必须管理上下文。

   了解这一阶段新增工具的职责边界。
5. [doc/logger.md](./logger.md)

## 和 Stage 1 相比，读者最该关注什么变化

这一阶段不要试图把“新增了多少工具”全记住，更重要的是理解下面三件事：

1. Agent 不再只是“问一句，答一句”，而是要在输出过程中持续工作。
2. 工具一多之后，就必须开始考虑哪些可以并发，哪些必须保守执行。
3. 对话历史不是无限免费的，系统需要开始主动管理上下文。

这三件事会直接决定 Agent 后面还能不能继续扩展。

## 读代码时建议关注什么

优先抓这几处：

- `internal/agent/agent.go`
- `internal/context/ctx.go`
- `internal/tools/registry.go`
- `internal/tools/*.go`

带着下面几个问题去读会更容易：

- 流式输出和普通输出的差别到底在哪里？
- 为什么工具不能全部无脑并发？
- 上下文压缩是在什么时候触发的？
- 新工具加入系统时，需要改哪些位置？

## 这一阶段还没彻底展开什么

虽然已经更像真正的 Agent 了，但这时项目还没有重点展开下面这些能力：

- Skill 体系
- Prompt 管理
- 更明确的任务系统
- MCP 扩展
- Session 持久化和更完整的 TUI

所以你会看到这个阶段已经开始“变复杂”，但还没有形成更清晰的能力层次。后面的 learning 分支，就是把这些层次逐渐补出来。

## 进入下一阶段前，你应该已经理解

- 为什么一个实用 Agent 一定会碰到输出体验、工具调度、上下文长度这些问题
- 为什么工具系统要开始出现分类，而不是所有工具都一样处理
- 为什么代码从 Stage 1 往 Stage 2 走时，复杂度会明显上升

理解这些后，再切到 `learn/stage-3-skill-prompt`，去看项目是如何开始引入“可复用提示词”和“任务/能力组织方式”的。
