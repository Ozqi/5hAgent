# 内部约定

## 名称

- 项目名和 GitHub 仓库名统一为 `walle`。
- Go module、CLI 命令、用户配置目录和项目数据目录统一为 `github.com/Ozqi/walle`、`walle`、`~/.walle`、`.walle`。

一句话：runtime 承担 Agent 工作，`walle daemon` 固定托管交互实例，文档和代码都先从简。

## 目录分工

| 路径 | 放什么 |
| --- | --- |
| `doc/` | 对外用户文档 |
| `.doc/` | 内部调研、决策记录、取舍记录 |
| `.TODO/` | 开发任务、待核验点、实现清单 |
| `.spec/` | 代码生成约束、架构图、拓扑事实源，按模块写职责、禁止事项和生成规则 |

## Runtime 边界

| 对象 | 只负责 |
| --- | --- |
| `runtime` | 持有 workspace、session/context、LLM、tools，并直接执行对话或通用 process |
| `walle daemon` | 固定托管可 attach 的交互 Runtime，并提供 socket 控制面 |
| `CLI/TUI` | 选择目标、输入、展示事件 |

## 当前固定点

- 控制 socket 先用 `~/.walle/run/supervisor.sock`。
- 全局默认配置只放 `~/.walle/settings.json`；不做项目级 settings。
- 运行进程查询统一走 `supervisor.sock` 的 `ProcessSnapshot`；不维护第二套 runtime state 文件。
- 模型切换只更新当前 Runtime 内存；需要修改默认模型时更新 `settings.json`。
- 首版目标协议只留 `list / attach / input / stop`；当前代码另有客户端断开的内部 `detach` 消息。
- runtime / daemon 设计见 [runtime-daemon-boundary.md](runtime-daemon-boundary.md)。
- runtime 对外接口见 [runtime-interface.md](runtime-interface.md)。
- 设计影响记录见 [design-change-log.md](design-change-log.md)。
- 代码注释使用中文；代码标识符、命令、错误文本和外部 API 名称保持原文。
- `.gitignore` 已放行 `.doc/`、`.TODO/` 和 `.spec/`。

## Context 约定

- 已加载上下文对用户透明，TUI 应展示关键状态。
- worklog 和 TUI 尽量拿到同一份 runtime 事件。
- session 负责持久化；ctx 负责本轮模型上下文，两者可以分离。

## 项目特色

一句话：让 Agent 透明运行，让你控制发给模型的上下文。

| 特色 | 说明 |
| --- | --- |
| Go 实现 | 单二进制、部署简单、并发和长期运行心智清楚。 |
| 代码少 | 优先小 core，少抽象，少依赖，读代码的人能快速掌控。 |
| Runtime 优先 | Agent 是可直接运行的本地实例；TUI、CLI、daemon 都只是入口或管理层。 |
| 透明运行 | session、tool call、worklog、失败原因尽量可见，方便复盘。 |
| 可控上下文 | 本地保留完整上下文，发给 LLM API 的内容走投影层。 |
| 小核心扩展 | tools、skills、terminal commands、plugins/capabilities 都挂在 runtime 外围。 |
| 多 Agent 自举 | 保留 `walle ps/attach` 与通用 process 能力；任务编排优先交给 Skill、MCP 或外置动态工具。 |

## 规划顺序

1. 先稳住 runtime：`New`、attach、session、通用 process worklog、`ProcessSnapshot`。
2. 再做上下文投影：mask、pin、debug request、压缩路径统一走投影。
3. 再做能力挂载：terminal 动态工具和 Cordis-like 插件生命周期，示例插件只做验收 fixture。
4. 多 Agent 先复用 `walle ps/attach`、通用 process 和 Bash/Terminal 工具自举；Web console、sandbox、插件市场等到真实需求出现。

## 取舍规则

- 能用 Go 标准库解决的，不引入新依赖。
- 能用一个清晰函数解决的，不新增框架。
- 能作为 skill、脚本、terminal command 的能力，先不进 runtime core。
- 多 Agent 协作优先走现有 CLI 和全局观察能力；有重复人工流程后再沉淀专用命令。
- 代码行数增长要服务真实行为；新增抽象需要两个以上真实调用点。
- 对外叙事围绕 `透明运行` 和 `可控上下文投影`，避免泛泛宣传 agent harness。
