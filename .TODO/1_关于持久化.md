# 关于持久化

agentd的“落盘设计” 和 runtime自身的session持久化有一定的冲突。

前者的设计理念是认为 agent proceess 工作所在的上下文，仅仅是工作过程中产生的输入输出（临时变量），对于关键信息，应该自行显示地持久化（又agent自己主动进行）

但是runtime自身需要拥有基本的会话恢复能力

## 确定结论

- 不再为 daemon/AgentProcess 设计第二套 session 持久化。
- Runtime 现有 session 是“用户会话恢复能力”，归 `internal/context` 管理，默认落到 `~/.5hAgent/sessions/`。
- AgentProcess 的 report/worklog 是“执行产物”，归项目 `.5hagent/` 管理，用于验收和追踪，不等价于可恢复上下文。
- 如果某个 Agent 想把关键状态转成长期知识，应通过工具显式写文件；这属于 Agent 行为，不属于 systemd 调度核心。
- 后续实现不要恢复 `sys.session` 这类 LLM 可见的重复 session 工具；会话恢复由 runtime/context 自动管理。
