# 动态终端工具

## 命名结论

工具名统一使用：

```text
<domain>[.<resource>...].<action>
```

规则：

- 最后一段是 action。
- 前面的段是 domain path。
- `rootDomain` 用于工具分组展示，例如 `terminal`、`context`。
- 完整工具名全局唯一注册。
- 默认控制在 2 到 3 段；超过 3 段时优先把层级收进参数。

公共终端域名：`terminal`。

- 稳定管理工具：`terminal.manage`。
- 稳定执行工具：`terminal.run`。
- 子资源工具可用：`terminal.session.create`。
- 动态工具可用：`terminal.<name>.<action>`，例如 `terminal.repo_diff.check`。
- 临时脚本也注册成 `terminal.<name>.<action>`，由注册元数据路由到临时执行器。
- 第一版只做运行期注册，不落盘。

内部包名可以叫 `terminal`，局部变量和未导出类型可以按现有代码风格缩短为 `term`。

## 当前结论

一句话：`terminal` 是 LLM 和终端可执行命令之间的薄封装层；动态工具统一放在 `terminal` 域，以 `terminal.<name>.<action>` 暴露；命令模板和临时脚本都由同一套 registry 管理，并按注册元数据路由到对应 executor。

这个设计目标是提高 LLM 调用正确率，同时保持 Runtime 小。

## 从 LLM 调用正确率看

模型最容易稳定发出的请求应该长这样：

```json
{"paths":"AGENTS.md CLAUDE.md"}
```

对应工具名：

```text
terminal.repo_diff.check
```

这个形态比让模型调用通用入口再填写 `action/name/args` 更直接：

```json
{"action":"run","name":"repo.diff_check","args":{"paths":"AGENTS.md CLAUDE.md"}}
```

动态工具可见时，模型只需要选中正确工具名，再填少量业务参数。

注册请求由管理工具完成：

```text
terminal.manage
```

```json
{
  "action": "register",
  "name": "repo_diff",
  "description": "检查指定文件的 diff 空白错误",
  "command": "git diff --check -- {{paths}}",
  "args": {
    "paths": {"type":"string", "default":"."}
  },
  "timeout": "15s",
  "cwd": "workspace",
  "read_only": true
}
```

注册成功后，下一次模型调用应能看到新工具：

```text
terminal.repo_diff.check(paths: string)
```

避免让模型发送这类请求：

```json
{"tool":{"terminal":{"registry":{"operation":{"kind":"execute"}}}}}
```

原因：层级深、同义枚举多、互斥结构多，模型容易填错。

## 工具接口草图

稳定管理工具：`terminal.manage`

Action：

- `register`：注册一个命令模板。
- `list`：列出当前 runtime 内已注册命令。
- `unregister`：删除一个注册命令。

动态执行工具：`terminal.<name>.<action>`

示例：

- `terminal.repo_diff.check`
- `terminal.go.build`
- `terminal.symbol.find`

第一版必填字段：

| 入口 | 必填字段 | 说明 |
| --- | --- | --- |
| `terminal.manage/register` | `name`, `description`, `command` | `args/timeout/cwd/read_only/shell` 都有默认值 |
| `terminal.manage/list` | 无 | 返回 name、description、args 摘要 |
| `terminal.manage/unregister` | `name` | 只删当前 runtime 内存态 |
| `terminal.<name>.<action>` | 按注册时的 args schema | 缺省字段使用 default |

## 注册表边界

- 第一版注册表只放 runtime 内存，不落盘。
- 每个 runtime 持有自己的注册表，daemon 服务多个 runtime 时互相隔离。
- 通用 process 内注册的工具随该 process 结束消失。
- 交互 Runtime 内注册的工具随 daemon 退出消失。
- 注册成功后需要刷新下一轮 LLM 可见工具列表；实现时只在注册表变更后重建工具绑定，避免每轮无意义刷新。
- 后续确实需要复用时，再考虑从 skill 或 `.walle/tools/*.json` 启动加载。

## 执行边界

- 默认使用当前环境 shell。
- 只有 spec 明确写 `shell: "bash"` 时才使用 Bash。
- `command` 使用模板参数替换，不使用 `eval`。
- 参数替换必须做 shell quote。
- `timeout` 必须有默认值，例如 `30s`。
- stdout/stderr 返回需要裁剪，保留 exit code。
- `read_only` 第一版作为元数据和 UI 提示，不先实现完整权限系统。

## 错误信息要求

错误要帮助模型下一次改对请求。示例：

```text
unknown terminal tool "terminal.repo_diff.check"; call terminal.manage with {"action":"list"} or register it with {"action":"register",...}
```

```text
missing field "paths" for terminal.repo_diff.check; example: {"paths":"AGENTS.md CLAUDE.md"}
```

```text
invalid action "exec"; allowed: register,list,unregister; example: {"action":"list"}
```

## UI 和日志

真实 ToolCall 名称直接显示动态工具名：

```text
◆ Ran terminal.repo_diff.check
```

worklog 记录：

- tool name
- rendered command 摘要
- cwd
- shell
- timeout
- exit code
- stdout/stderr 摘要

1. 读现有 `base.exec_shell`、`tools.Registry`、tool event UI 的实现边界。
2. 增加 `terminal.manage` 和动态 `terminal.<name>` 的类型草图与中文注释，先确认输入输出字段。
3. 实现 runtime 内存注册表，挂到 runtime 或 tools registry 能访问的位置。
4. 实现 `terminal.manage register/list/unregister`，先不执行动态命令。
5. 注册表变更后，刷新 Agent 的工具 map 和 model tools 绑定；只在下一轮 LLM 调用前刷新。
6. 复用现有 shell 执行逻辑实现动态 `terminal.<name>.<action>`。
7. 增加错误提示，保证错误里有字段名、允许值和修正示例。
8. 用一个只读命令做 process/TUI 验收：注册 `terminal.repo_diff.check` 后执行。
9. 阶段收尾时再补对外文档或开发日志。

## 暂不做

- 目录热加载。
- 全局持久注册表。
- 多语言 runner。
- 完整权限系统。
- 远程 daemon 共享注册表。
- 让动态工具跨 runtime 自动同步。

## tmux 执行承载

Terminal 动态工具执行时可以复用 tmux 承载长任务，先作为 executor 的一个实现细节，不单独设计 job system。

第一版目标：

- 短命令仍返回 stdout/stderr、exit code。
- 长任务返回 tmux target、启动命令和最近输出片段。
- 同一个 target 后续可继续 capture，避免 tool call 结束后丢进程。
- session/window 命名保持可读，例如包含 workspace、task/process id 或时间戳。
- 保留 `direct` 执行路径，用于极短、无状态、需要精确 stdout 的命令。
- TUI、通用 process、daemon 共用同一命名策略。
